OSAI: AI Infrastructure and Deployment Exploits

9.1 THE INFRASTRUCTURE LAYER
Definition: everything that hosts and serves an AI system in production
Components: server, framework, GPU/orchestration, APIs, cloud identity
Identity: cross-cutting — bounds how far any compromise can spread
Backlink: Module 1 Obj 1.2 layer 5; Module 8 Obj 8.3 model-loading
Why high-leverage: the common foundation under every earlier layer
vs conventional infra: same mechanisms, GPU-bound cost + model loading are new
9.2 EXPOSED SERVING SURFACE
Weak mgmt auth: "internal-only" assumed instead of enforced
Debug endpoints: same M6 6.2 exposure pattern, at the serving layer
Cross-request leakage: batching/KV-cache reuse blurs isolation
vs web API exposure: same categories, AI-specific mechanisms
Recognise it: inconsistent auth across endpoints around one model
Framework: OWASP LLM02 for disclosure/leakage outcomes
9.3 CLOUD IDENTITY & PRIVILEGE
Root cause: convenience provisioning, never revisited
Metadata service: internal-only credential source, reachable via SSRF-style forgery
Chain: foothold → identify identity → enumerate perms → pivot
Least privilege vs convenience: convenience is the default outcome
Framework: no dedicated OWASP LLM category — conventional cloud risk
Report as: excess privilege + compromise path, cite cloud-security guidance

EXAM TRAPS & ACRONYMS
⚠️ Denial of wallet can succeed with zero availability impact — cost, not uptime, is the property attacked
⚠️ "Internal-only" is a network assumption, not authentication — verify management interfaces directly
⚠️ Cloud identity/privilege escalation from infra has no dedicated OWASP LLM category — report it as a conventional cloud risk
⚠️ Cross-request leakage via batching/KV-cache is the serving-layer twin of Module 6's cross-tenant vector risk
⚠️ Multi-tenant resource isolation failure is an availability risk, distinct from multi-tenant data-isolation failure
