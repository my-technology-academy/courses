OSAI: Reconnaissance for AI Targets

2.1 PASSIVE RECON
Passive recon: public sources only — zero traffic to the target
Sources: docs, client-side code, job postings, blogs, model cards
Model card: describes the base model, not the deployed app
Managed API: vendor controls guardrails — recon focuses on the app
Self-hosted: reopens the infrastructure layer (Module 9)
Order: always passive before active — free, unlimited, low-risk
2.2 ACTIVE FINGERPRINTING
Fingerprint signals: style, limits, guardrail boundary — triangulated
Self-reported ID: a hint only — never corroborated fact
Graded probing: baseline → limits → edge case → boundary → correlate
Guardrail mapping: input vs output enforcement, consistency
Black-box: nothing known · Grey-box: some docs shared
2.3 SURFACE ENUMERATION
RAG signal: org-specific answers + citation-like references
Tool signal: real side effects, latency spikes, delegation language
Multi-agent signal: coordination language, capability shifts
Infra signal: API versioning, exposed serving endpoints
Order: reachability → retrieval → tools → agents → infra

EXAM TRAPS & ACRONYMS
⚠️ Self-reported model identity is a hint, not evidence — corroborate before relying on it
⚠️ Skipping passive OSINT wastes rate-limited, costed active probes on public information
⚠️ Confirming a tool exists is not the same as exploiting it — stop once confirmed
⚠️ A single fingerprinting signal is weak; only triangulated signals produce a confident fingerprint
⚠️ Recon output is only useful once documented as evidence — undocumented recon is wasted recon
⚠️ OSAI weightings are not published — the exam is a 24-hour practical engagement
