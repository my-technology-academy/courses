OSAI: Exploiting RAG Pipelines

5.1 RAG ARCHITECTURE
Pipeline: ingest → chunk → embed → store → retrieve → augment
Chunking: splits documents into retrievable units — a deliberate lever
Embedding: converts a chunk to a vector; content-blind to trust
Retrieval: similarity search, ranked by vector closeness only
Augmentation: retrieved text enters context — the trust boundary
RAG vs fine-tuning: live editable pipeline vs training-time supply chain
5.2 CORPUS POISONING
Definition: malicious content planted at the ingestion stage
Persistence: one poisoned doc affects every future matching query
Vectors: wikis, uploads, scraped web content, feedback/tickets
Lifecycle: find ingestion point → craft → ingest → index → persist
Framework: OWASP LLM04 — Data & Model Poisoning
vs direct injection: plants data, no live interaction needed
5.3 INDIRECT INJECTION
Mechanism: retrieved chunk treated as trusted instruction, not data
vs direct: no access to victim's own prompt required
Why worse: scales to every user whose query retrieves the chunk
Trust chain: query → retrieve → augment → trust → act
Framework: OWASP LLM01 — Prompt Injection (indirect sub-case)
Recognise it: effect tracks retrieved content, not query wording

EXAM TRAPS & ACRONYMS
⚠️ RAG-corpus poisoning attacks the ingestion stage, not the model's weights — no training compromise required
⚠️ Indirect injection via retrieval needs no access to the victim's own prompt — that is exactly what makes it scale
⚠️ Persistence means a poisoned document affects every future matching query, not just one conversation
⚠️ Cross-tenant leakage can occur through an ordinary query — no attacker payload is required at all
⚠️ Chunk-boundary and citation-spoofing technique are separate from poisoning and injection — know all four of 5.4
⚠️ OSAI weightings are not published — the exam is a 24-hour practical engagement
