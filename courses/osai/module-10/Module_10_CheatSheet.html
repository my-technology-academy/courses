10.1 ROLE IN THE LIFECYCLE
Definition: turns a mapped attack surface into a ranked set of attack paths
Inputs: M2 target inventory + M1 Obj 1.4 scoping objectives
Output: ranked attack paths, each with evidence, layer, impact/effort
Lifecycle position: phase 3, between recon and exploitation
vs recon: recon discovers what exists; this decides what to attack first
vs exploitation: produces a plan, not evidence — no payload delivered
10.2 CONSTRUCTING ATTACK PATHS
Attack path: ordered weakness chain from start to a stated objective
Enumeration vs viable path: confirmed ≠ tied to an objective
Mechanism: start from objective → find leverage → chain layer by layer
Single vs chained: chained paths usually demonstrate higher impact
Confidence: confirmed vs hypothesised — chain is as strong as weakest link
Backlink: M1 Obj 1.1 red teaming = chaining weaknesses to prove impact
10.3 PRIORITISING BY IMPACT/EFFORT
Two dimensions: impact (severity) vs effort (time/skill/opportunity)
Priority order: high-impact/low-effort → high-impact/high-effort → low-impact
Asset criticality: impact weighted by how much the client values the asset
Framework inputs: OWASP category, ATLAS tactic stage, confidence, chain depth
Workflow: list → score impact → score effort → sort → revisit
Pitfall: chasing novelty over impact; never revisiting the ranking

EXAM TRAPS & ACRONYMS
⚠️ Confirming a component exists (enumeration) is not the same as a viable attack path — a path must be tied to a stated objective
⚠️ The most severe single finding is not automatically top priority — impact is weighed against effort and asset criticality together
⚠️ A threat model is not fixed once written — exploitation evidence feeds back into the ranking throughout the engagement
⚠️ Framework mappings (OWASP/ATLAS) are prioritisation inputs, not just report vocabulary
⚠️ A chain's confidence is only as strong as its weakest, least-verified link
⚠️ OSAI weightings are not published — the exam is a 24-hour practical engagement
